# 29 — Story Threads

How the app knows that a story is the fourth update on something rather than a standalone item.

A **thread** is the set of stories in one topic about the same *developing subject*. Every story has a `threadId`, and a story that joined nothing carries its own id — so a thread of one is the ordinary case and needs no special handling anywhere downstream.

This is the foundation of the "story so far": once stories are grouped, a card can show its own history (NEWS-281, NEWS-282) instead of presenting the fifth twist in an ongoing saga as though nothing had come before it.

## Threading is not deduplication

They are different questions, and conflating them is the mistake this doc exists to prevent. See [2 — News Checks and Deduplication](2-news-checks-and-dedup.md) for the other half.

| | Dedup (`dedupeKey`) | Threading (`threadId`) |
|---|---|---|
| Question | *Is this the same article?* | *Is this the same story unfolding?* |
| Built from | the first source's normalized URL (`host+path`), falling back to the normalized title | title similarity, entity overlap and recency across the topic's history |
| Compared how | **exact string match** against `store.dedupeKeysForTopic()` | scored, with thresholds |
| Outcome | the story is **dropped** | the story is **kept and grouped** |

- **FR-29.1** *(Shipped)* Threading is computed, not derived from `dedupeKey`. A dedupe key has no notion of subject: two outlets covering one event produce two different keys, which is precisely why the same event can already appear twice in a feed. Nothing about two keys' proximity says anything about whether the stories are related — `url:news.example.com/a` and `url:times.example.com/b` are as far apart as any two strings.
- **FR-29.2** *(Shipped)* Dedup runs first and threading second, on what survives. Dedup decides what is *stored*; threading only ever describes stored stories. A story dropped as a duplicate never had a thread to be in.
- **FR-29.3** *(Shipped)* Threads are **per topic**, like dedup (FR-2.9). The same event under two topics is two stories, and they are in two different threads — because a thread is read within a topic's feed, and "the story so far" for *Flooding* is not the same narrative as for *Infrastructure*.

## The data model

- **FR-29.4** *(Shipped)* `NewsItem.threadId: string` (`src/db/schemas.ts`), stored as `items.thread_id` with the index `items_topic_thread(topic_id, thread_id)`.
- **FR-29.5** *(Shipped)* A thread is named by **the id of its first story**, not a synthetic group id. A thread always has a story that started it, so inventing a second kind of identifier would mean two things to keep in step and a group id that could outlive its stories.
- **FR-29.6** *(Shipped)* **Every story is a thread of one until something joins it.** `threadId` defaults to the story's own id — on write (`Store.addItems`) and on read (`NewsItemSchema`, which reads an empty stored value as the row's own id). So no reader ever has to handle "unthreaded": the thread of a lone story is that story.
- **FR-29.7** *(Shipped)* Validated on read like every other field. The schema is a `z.object(...).transform(...)` rather than a plain object precisely so the default can refer to a sibling field; nothing crosses the boundary with a cast.
- **FR-29.8** *(Shipped)* `Store.threadForItem(id)` returns a story's whole thread **oldest first** — a thread is read as a sequence, because the point of showing it is *how we got here*. Flagged stories are left out, matching what the feed shows (see [15 — Off-Topic Flagging](15-off-topic-flagging.md)), except the requested story itself: answering "nothing" about a story someone is looking at would be a worse lie than showing it. An unknown id returns an empty list.

## The signals

All local, in `src/threads.ts`: pure functions, no I/O, no model call, no cost. That is what lets the same code thread stories as they land *and* group rows already in the database.

- **FR-29.9** *(Shipped)* **Content-word overlap.** Titles are normalized with the same `normalizeTitle` dedup uses, crudely singularized (a trailing `s` dropped, so "recall" and "recalls" are one word), and reduced to words of three characters or more that are not stopwords.
- **FR-29.10** *(Shipped)* **The topic's own name is a stopword.** Inside a topic, the topic's words are shared by nearly every story it will ever produce, so counting them as evidence would thread the whole topic together. This single subtraction does more for precision than the stopword list does: it is what keeps "Major development in Formula One" and "Formula One: what experts are watching next" apart.
- **FR-29.11** *(Shipped)* **Capitalized-entity overlap** — a cheap stand-in for proper nouns, taken from the raw title. A headline's first word is capitalized whatever it is, so this over-collects by about one word per title; that is why entity overlap **never authorizes a join on its own**. It only lowers the content-word requirement.
- **FR-29.12** *(Shipped)* **Shared source host is a tie-breaker only** (a quarter of a point), never what lifts a pair over the line. Within one topic the same outlet recurs constantly, so "both from reuters.com" is nearly no information — and the interesting case is the opposite one, two *different* outlets on one subject.
- **FR-29.13** *(Shipped)* **A recency window** (`THREAD_MAX_GAP_MS`, 30 days) measured pairwise as an absolute gap. A thread that keeps being updated therefore keeps extending indefinitely — each update is close to the one before — while a subject nothing has touched for a month stops accreting, because the anniversary piece is a new story rather than the next instalment. Absolute, not signed, so a story arriving out of chronological order is judged the same way.
- **FR-29.14** *(Shipped)* A story whose `foundAt` cannot be parsed joins nothing. An unusable timestamp means the recency window cannot be evaluated, and the bias is to leave it alone.

### The thresholds, and why they are set low-recall

- **FR-29.15** *(Shipped)* A pair joins only when **all** of these hold: within the recency window; **three shared content words**, or **two** when at least one capitalized entity is also shared; and the shared words are **at least 40%** of the shorter title's content words.
- **FR-29.16** *(Shipped)* **A false join is worse than a missed one, and the thresholds are tuned accordingly.** Missing a thread leaves a story looking standalone — which is what every story looked like before this existed, so the cost is zero new wrongness. A false join files a story under a headline it has nothing to do with, and presents that with the same confidence as a real one. So every gate is set to leave items unthreaded when the evidence is thin.

### Pairwise-nearest, never a merge

- **FR-29.17** *(Shipped)* A story joins the thread of the **single best-matching individual story**: strongest score, then closest in time, then lowest id (so the outcome is deterministic, not dependent on row order).
- **FR-29.18** *(Shipped)* **Membership is transitive by emergence, not by union.** C matching B takes B's thread, which may be A's, so chains form naturally. But a story resembling two existing threads picks one — the threads are never merged. Merging is where transitive clustering drifts: one weak bridge silently welds two unrelated runs of stories into a single "story so far", and afterwards there is no evidence left of which link was the bad one. Emergent chaining still drifts a little, and the recency window is what bounds it: a subject has to keep being updated to keep growing.
- **FR-29.19** *(Shipped)* **An already-decided thread id is never rewritten** by threading a new story. A thread the user has already seen cannot reshuffle underneath them.
- **FR-29.20** *(Shipped)* **Flagged (`offTopic`) stories do not participate.** They neither join threads nor offer themselves as match targets: the user has said the story does not belong to this topic, so it must not become the spine of a thread. Flagging a story *after* it joined one does not un-thread the row — it only stops `threadForItem` showing it (FR-29.8), so unflagging restores the grouping rather than having to recompute it.

## When threading happens

- **FR-29.21** *(Shipped)* **At check time**, in `CheckRunner.checkTopic` — after `filterNewItems` and before the insert, against the topic's history read fresh at that moment (not the `known` list taken before a multi-minute provider call). Stories in one batch are threaded against each other as well as against history, so two outlets' coverage arriving in the same check lands in one thread. Item ids are minted in the runner rather than by the store, because thread assignment refers to sibling stories by id.
- **FR-29.22** *(Shipped)* **A backfill at startup** (`Store.backfillThreads()`, called from `src/cli.ts` after the retention prunes so it never threads a story about to be deleted). It groups what is already stored — rows from before this existed, and rows that arrived out of chronological order.
- **FR-29.23** *(Shipped)* The backfill is **deterministic**: each topic is replayed strictly in `(found_at, id)` order and a story is only ever matched against stories *before* it, so an assignment never depends on what arrived later. Chronological replay is the canonical assignment; a story that arrived late gets the grouping it would have had if it had arrived in order.
- **FR-29.24** *(Shipped)* The backfill is **idempotent**: `thread_id = id` (a thread of one) is the "not yet grouped" marker, a story that recomputes to a thread of one recomputes to the same thing forever, and rows that already joined a thread are skipped outright. Running it twice changes nothing the second time — which is what makes it safe to run on every start, and what the tests assert directly.
- **FR-29.25** *(Shipped)* The schema migration (v4 → v5) sets every existing row's `thread_id` to its own id. Existing stories become threads of one, which is exactly what they were, and the invariant "a thread id names a story" holds from the first read; the backfill then groups them for real.

## What this does *not* do

- **FR-29.26** *(Decided)* **No model-reported linking.** A check could in principle be asked "does this continue known story X" — it already sees the last 60 titles (`MAX_KNOWN_ITEMS`) — and that would raise precision. It cannot replace this layer: the window will not reach a thread whose last update was months ago, and it cannot label stories already in the database. Filed separately (NEWS-284).
- **FR-29.27** *(Decided)* **No model-written summary of what changed.** Threading says which stories belong together; nothing here says *what is new* in an instalment relative to the one before it. That would be a model call per story, and the timeline below answers the question well enough without one — the headlines in order *are* the account of what changed.

## The timeline in the card ("the story so far")

What the expanded pane (NEWS-281) is filled with (NEWS-282), and what tells a reader it is worth opening (NEWS-283). This is the payoff of the whole feature and it costs **no AI spend**: everything below is a query over stories already stored.

- **FR-29.28** *(Shipped)* **`GET /api/items/:id/thread`** returns `{ items }` — the story's whole thread, oldest first, from `Store.threadForItem` (FR-29.8). Its own route rather than part of the feed page: a thread is several *whole* stories, and multiplying a size-sensitive payload ([17 — Server-Side Pagination](17-server-pagination.md)) by the average thread length would pay for a pane nobody has opened. An id the store does not know answers **404** with a message, not an empty timeline — `threadForItem` always answers with at least the requested story, so "empty" can only mean "no such story", and an empty timeline would state something false about a story that is gone (retention, or a stale card).
- **FR-29.29** *(Shipped)* **The feed page carries each story's thread *shape*** — `threads: Record<storyId, { position, size, startedAt }>` on `ItemsResp`, from `Store.threadSummaries`. Three numbers a story wide, and **only for stories whose thread holds more than one**, so a feed with no threading yet carries an empty map and the response is what it always was. That is what lets a collapsed card show a badge with no request of its own (NEWS-283) *and* what tells the client an expansion has nothing to fetch. Flagged stories are excluded from the counting, so the badge's position and the timeline's rows cannot disagree; a flagged story therefore has no summary at all, which is correct because review-mode cards do not expand (FR-3.66).
- **FR-29.30** *(Shipped)* **Fetched on expand, never on render, and cached.** A fetch per card would be a hundred requests for a feed nobody has clicked. `loadThread` (`src/client/api.ts`) skips the request entirely when the page carries no summary for the story — the common case — and reuses a cached timeline across collapse/re-expand. The cache is keyed on the story id **and the size it was fetched at**: the 4-second poll refreshes the badge, so a thread that has grown announces itself and is re-read rather than served stale. An in-flight request is not duplicated, and an error is never cached.
- **FR-29.30a** *(Shipped, NEWS-293)* **An open pane follows its thread.** `refreshFeed` calls `loadThread` for the expanded card on every poll, so a thread that gains an instalment while someone is reading it grows in place instead of waiting for a collapse and a re-open. The badge shape in `threads` has just been refreshed at that moment, which is the only point the client can know a thread grew.

  **No new reactive edge**, which was the reason this was left out of NEWS-282: FR-29.30's size check *is* the mechanism. A poll that finds the thread unchanged — overwhelmingly the common one — returns without a request, so calling this every four seconds costs nothing.

  Two things make it a refresh rather than a re-fetch. The pane **keeps its rows on screen while the bigger thread loads**: the first-load path sets `loading`, which renders as "Looking up the story so far…", and reusing it here would blink a correct timeline out every time the thread grew — the old rows are still true, just one instalment short for a moment. And a **failed refresh changes nothing**: the reader asked for nothing, so a background failure must not swap a good timeline for an error with a retry button (FR-29.35 is about a read someone *requested*), and the next poll tries again anyway. Because a refresh deliberately leaves the pane `ready`, "is a request in flight" stopped being readable off the pane's status and is tracked separately — otherwise every poll during a slow request would start another.

  The feed does **not** wait on it. The four-second tick owes the reader the feed; blocking that on a per-card timeline would let one slow thread stall everything.

- **FR-29.31** *(Shipped)* **The rows are capped at `THREAD_ROW_CAP` (4), with "Show all N stories".** Cards lay out in a grid whose rows stretch to the tallest card on the line (FR-3.37), so an uncapped timeline on a long-running subject grows the whole row and pushes the rest of the feed off screen — the opposite of what expanding one story should do to the others. **The most recent rows survive the cap**: the pane is read beside the story you clicked, so its neighbours are what explain it, and the distant origin is what "show all" is for. The label counts the *whole* thread ("Show all 6 stories") because "how much history is there" is the question a capped list raises. Lifting the cap belongs to the pane that is open, not to the reader — the feed is an accordion, so one flag suffices and opening any card puts the cap back.
- **FR-29.32** *(Shipped)* **A thread of one gets one honest line and no heading.** Most stories are the only thing we have on their subject, especially before history accumulates, so this is the *ordinary* pane rather than an edge case: "Nothing else on this subject yet — later stories about it will collect here." A "The story so far" heading over nothing reads as a bug rather than as an answer, so the heading only appears where there is a timeline to head.
- **FR-29.33** *(Shipped)* **A row's headline is a link to that story's own source; nothing else in the row is interactive.** That is the only destination a row can promise. Scrolling the feed to that story's card would silently do nothing in the common case — a thread reaches back 30 days and the feed holds one page — and a row that looks pressable and isn't is worse than a plain row. A story with no usable source renders as plain text, so what looks like a link always is one. Links carry `data-external="1"`, so the desktop shell opens them in the system browser like every other source link (FR-3.8).
- **FR-29.34** *(Shipped)* **The story being read is a row in its own timeline, marked rather than filtered out.** It carries `aria-current="true"` and a quiet "this story", and is not a link. That is what gives the pane a "you are here" without a second mechanism, and it is why the count in "Show all N" agrees with the badge's N instead of being one short.
- **FR-29.35** *(Shipped)* **A failed lookup stays in the pane**, with the server's message and a "Try again" button — not in the page's error banner. One card's background read failing is not worth a red bar across the app, and the pane is where the person who asked is looking. Retrying and re-opening the card are the same path, because an error is not cached.
- **FR-29.36** *(Shipped)* **A collapsed card in a thread wears a badge, and the badge *is* the expander** (NEWS-283). Without it the timeline is invisible: nothing on a collapsed card would say that a click reveals anything, and the feature would ship undiscovered. So the expander — already a real button with `aria-expanded`/`aria-controls` (FR-3.65) — grows a label instead of gaining a sibling: one control, whose accessible name says both what pressing it does and what it would reveal ("Show the story so far — 4th update · since Jun 12"), rather than a count a screen reader would read as a riddle. A second element would be either inert chrome or a second control in a header with no room for one.

  - **Only for a thread of two or more**, from the feed page's summary (FR-29.29) — **never a fetch per card**. A badge on every card would be noise and would say nothing about *which* cards hold history.
  - **Two phrasings, because there are two honest facts.** A story that followed others is "the 4th update", and the second half worth saying is when the subject started. The story that *began* a thread updated nothing, and its own date is already beside it, so it reads "3 follow-ups" instead. "1st update" would be wrong in the one place the app cannot afford it — the sentence that has to earn the click.
  - **The card shows the count; the date rides the tooltip and the accessible name.** Measured, not guessed: a feed column is ~430px in the two-column layout, and "· since Jun 12" pushed the topic pill from one line onto three — precisely the crowding recorded in FR-3.2c/NEWS-71. The date is not lost; the pane it opens dates every row. The visible text is carried into the accessible name **verbatim**, so WCAG 2.5.3 (Label in Name) holds.
  - `dayLabel`'s words, lowercased ("since today" / "since Jun 12"), so the badge and the feed's day heading name a day identically. There is no third date format in the app — which is why `dayLabel` lives in `src/client/dates.ts`.

## Tests

- **Unit** — `tests/unit/threads.test.ts`: the similarity module directly (same-subject/different-outlet pairs join; unrelated stories in one topic do not; stopword-only and topic-name-only overlap do not; the ratio gate; the recency cutoff on both sides; flagged stories excluded), then the store's round-trip, `threadForItem`, and the backfill's idempotency (run twice, identical mapping and a second-pass count of zero).
- **Transition matrix / adversarial** — in the same file, because this module is stateful across a topic's whole history: empty → thread of one → thread of two → a second thread; a live thread extending past the window from its oldest member; a thread going quiet and reviving (and what follows joining the *revival*, not the stale thread); stories arriving out of chronological order; a topic cleared and refilled (asserting no new story inherits a cleared story's id); an undo restoring the ids it took; a mid-history story arriving late and being regrouped by the next backfill; the same subject twice in one batch; stories orphaned by a deleted topic.
- **Migration** — a pre-thread (v4) database is opened, keeps both stories, and threads them. The regression it pins is **data loss**, not a missing column: `items_topic_thread` was first created alongside the tables, which run *before* the migrations, so opening any existing database threw `no such column: thread_id` — which `Store` correctly reads as corruption and answers by backing the file up and starting fresh. `src/db/sqlite.ts` now runs **TABLES → MIGRATIONS → INDEXES**, and that ordering holds for every future column too.
- **Timeline unit** — `tests/unit/thread-timeline.test.ts`: `Store.threadSummaries` (position/size/first-seen; nothing at all for a thread of one; a flagged story dropped from the count *and* given no entry of its own; a page spanning two topics); the route through `createApp` + `app.request` (whole thread oldest-first, a thread of one, a flagged member excluded but still answered *about*, 404 on an unknown id, summaries on the feed page and an empty map when nothing is threaded); the pane's pure rules (the cap keeps the recent rows, the show-all count, one date format shared with the feed heading); and the client cache as a **sequence** — fetched once, reused across re-expands, refetched when the thread grew, not duplicated in flight, an error surfaced in the pane and retried, and two cards' panes interleaved.
- **Badge unit** — `tests/unit/thread-badge.test.ts`: the label as *text*, because what it says is the whole feature. The ordinal including the 11th/12th/13th exceptions (a thread that long is exactly where a badge is read closely), the first story's "3 follow-ups" / "1 follow-up" with no date clause, the date reused from `dayLabel` rather than reinvented, an unparseable start date dropping the clause instead of printing half of one, a thread of one producing nothing, and the expander's accessible name — including that it **contains the visible label verbatim** (WCAG 2.5.3).
- **The mock's series is itself asserted** in that file: three checks extend one subject to six stories, all in one thread, which is more rows than the cap. Without that property no browser flow could reach "show all", so it is pinned where a change to the mock will trip over it.
- **E2E** — `tests/e2e/threads.spec.ts`: a check producing two outlets' coverage of one subject lands both in a single thread named by a real story's id, and the mock's default unrelated pair stays two threads of one. Reachable because the mock provider answers a topic whose name contains **"thread"** with a single-subject series (see [6 — AI Providers](6-providers.md)). Then the timeline: three checks build a six-story thread, the expanded pane shows four rows under "The story so far" with "Show all 6 stories", the current story is marked and unlinked, other rows link to their own source, show-all reveals the two oldest first, re-opening restores the cap — and a story with no thread shows the one-line note, **no heading, and makes no request at all**. The pane with a real timeline in it is axe-scanned in both schemes. The badge has its own test (NEWS-283): "2nd update" on the newer story and "1 follow-up" on the one that started the thread, the full label in the accessible name and tooltip, pressing it opening the timeline, none of it on a standalone story — and **no collision with bookmark/share at 420px, asserted as geometry** (left-to-right order, no overlap, one row, inside the card), because "does not crowd" is a question about pixels and a class assertion cannot answer it.

  **A test topic's name must not contain the series' own words.** The topic's words are stopwords inside it (FR-29.10), so a topic called "Riverside…" subtracts the word the series threads on and everything stays a thread of one — which reads as the feature being broken rather than as it working exactly as documented. Cost half an hour once; recorded here and in both test files.
