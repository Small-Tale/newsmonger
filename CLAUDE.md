# Newsmonger

Topic-based news tracker. The user enters topics; on a configurable interval (default 1 day) the app asks Claude — with web search — for genuinely new news per topic, deduplicates against previously reported stories, and shows summaries with source links in a feed.

## Tech Stack

- Node 22.5+ (built-in `node:sqlite`), TypeScript (strict), ESM
- [kerfjs](https://github.com/brianwestphal/kerf) 4.1 UI (JSX → HTML strings, signals + morph) — **read `.claude/skills/kerf-app/SKILL.md` before touching client code**
- Hono + `@hono/node-server` (localhost-only, default port 4187)
- Pluggable AI providers (`src/ai/providers/`, like `~/Documents/gitgist`) behind a `NewsProvider` interface — **only platforms that do their own web search** (Anthropic, OpenAI); default `anthropic` uses `@anthropic-ai/sdk` (`claude-opus-4-8`, adaptive thinking, `web_search_20260209`, streamed). See `docs/6-providers.md`.
- SQLite storage via built-in `node:sqlite` (`~/.newsmonger/newsmonger.db`; `--data-dir` / `NEWSMONGER_DATA_DIR` override). Rows validated with the same zod schemas on read; a legacy `data.json` is imported once (NEWS-94)
- Tauri v2 desktop shell (Node-sidecar architecture like glassbox; dev-mode only so far)
- esbuild + sass for client assets; tsup for the server bundle; eslint flat config with `strictTypeChecked` + `eslint-plugin-kerfjs`

## Architecture

`src/cli.ts` parses flags → constructs `Store` (SQLite), a `ProviderResolver` (resolves the active AI provider per check from settings, or the forced mock under `--ai-test`), and a `CheckRunner` → starts the Hono server (`src/server.ts`, DI via middleware) and the minute-tick scheduler (`src/scheduler.ts`). The client (`src/client/app.tsx`) is a kerf app polling `/api/state` every 4 s. AI providers live behind `NewsProvider` in `src/ai/providers/` (see `docs/6-providers.md`).

**Start every fresh session by reading `docs/ai/code-summary.md` and `docs/ai/requirements-summary.md`.** Requirements docs are numbered `docs/N-topic.md` (1–34, with 19 deliberately absent — NEWS-119 deleted it).

## Conventions

- **Type safety: validate, don't assert.** zod at every trust boundary (API request bodies, client-side state parsing, the data file, Claude's JSON output). No bare `as` casts to cross boundaries.
- **kerf client rules** (enforced by `eslint-plugin-kerfjs`, documented in `docs/3-ui.md`): state in `defineStore`/signals; events via `delegate()` with `data-*` attributes (never `addEventListener`/inline handlers); `data-key` on list rows; `.map()` not `each()` for static structural arrays. Plus two structural rules (see `docs/3-ui.md`): wrap conditional siblings (banners) in an always-present container, and keep `each()` containers structurally stable. **KF-377 — the kerfjs ≤2.0.1 bug these were written for — is fixed as of 3.0.0**, but the containers stay (NEWS-99): `#banners`/`#toast-slot` are ARIA live regions, which must exist *before* their content or the announcement is lost, and `#topics-panel` is the target of `aria-controls` (removing it fails the axe suite). They are ordinary good structure now, not scar tissue.
- The server readiness line `newsmonger running at <url>` is watched by `src-tauri/src/lib.rs` — keep the `running at ` marker in sync.
- Tests must never touch `~/.newsmonger` — use `tests/helpers/tmp.ts` (unit) or the Playwright-managed temp dir (E2E).
- The mock news service keys off topic names: containing "fail" → throws, "empty" → no items, "thread" → two outlets covering one subject (what makes story threading testable — NEWS-280); anything else → the same two deterministic stories every call (that's what makes dedup testable).

## Git

**Commit as you go — one commit per ticket, not one commit per session.** Don't wait to be asked, and don't batch a work session into a single giant commit: a 75-file commit spanning fourteen tickets is unreviewable, un-bisectable, and impossible to revert in part.

- **Commit when a ticket is done** — after its gates pass (typecheck, lint, unit, E2E) and its docs are updated, and before starting the next ticket. Commit the ticket's code, tests and docs together; they are one change.
- **Never commit red.** If the gates don't pass, the work isn't done — fix it or leave it uncommitted.
- **Message style**: `<Summary> (NEWS-NN)` subject, then prose explaining *why* and what was decided, bullets for substance, and a closing line for tests/docs. Long lines unwrapped. **No `Co-Authored-By` or `Claude-Session` trailers** — the user has asked for these to stay out.
- **Never `git push`** without being asked explicitly. Committing is routine; publishing is not.
- `npm run commit:msg` drafts a message from the staged diff with [gitgist](https://www.npmjs.com/package/gitgist). **Its output is a starting point, not a message to paste**: gitgist emits *Conventional Commits* (`feat:`, `build:`, …), which is not this project's convention. Take the summary of *what changed* from it and rewrite it in the style above — the subject line with the ticket id, and prose explaining why. gitgist reads the actual diff, so it is good at noticing changes a human would forget to mention, and bad at knowing which of them mattered.
- Commits land on `main` — that's this repo's history and the user's workflow. Don't open a branch unless asked.

## Editing this file

`CLAUDE.md` is part Hot Sheet **managed** and part ours, and the boundary is invisible unless you look for it:

- Anything between a `hotsheet:begin section=` marker and its `hotsheet:end` is **shared template text**. A sync rewrites it. An edit there is not "overwritten by a bug" — it is working as designed, and it fails **silently**, days later, in a commit about something else.
- A `hotsheet:begin specifics=` block, nested inside a managed section, **is ours** and survives sync.
- Everything outside any marker — Tech Stack, Architecture, Conventions, Git, this section — is also ours.

**So: anything project-specific goes in a `specifics` block, or outside the markers entirely.** NEWS-296 wrote its guidance into the managed half of *Requirements Documentation*; a sync returned it to the template, and the restored wording then told the next reader to hand-edit a file that is generated and gate-checked (NEWS-310).

Check the markers pair up after any sync. ## Testing Philosophy

- **Double coverage**: every feature covered by both unit tests AND E2E tests. Unit = logic in isolation; E2E = real user flows through the running app with minimal mocking.
- **Unit tests**: Mock external deps (filesystem, network), test real logic.
- **E2E tests**: As much as possible, use test automation tools to run realistic, user-facing flows. Minimize mocks.
- **Coverage**: Merge all test coverage (e.g. unit, E2E server, E2E browser) into one report. Low-coverage files should get more of both test types. Aim for 100% coverage of code lines, 100% coverage of branches, and 100% of features described in the requirements documentation.
- **Coverage is a floor, not a ceiling**: 100% line/branch coverage shows every line *ran*, not that every *behavior* — or every *sequence* of behaviors — is *asserted*. It is structurally blind to a **missing state transition**: a bug living in an untested interaction sails through a green 100% report because the individual lines still get hit by isolated, single-operation tests.
- **Transition-matrix testing for stateful modules**: for anything with modes / multiple code paths / a cache / a state machine, enumerate the states AND the transitions between them, then write tests that walk realistic multi-step sequences crossing state boundaries — not just each operation from a clean initial state.
- **Adversarial pass on stateful changes**: when adding or altering a stateful code path, deliberately try to break it with out-of-order / interleaved / repeated / empty-then-refill sequences; pin any that would have failed as permanent regression tests.
- **Manual test plan**: keep a manual test plan doc (e.g. `docs/manual-test-plan.md`) for features that can't be reliably automated. **Keep it up to date** — add such features there; when you add automated coverage for a previously-manual item, remove it and note it in an "Automated Coverage Summary".
- **Always fix lint and type errors before finishing**: Fix as you go, don't batch.

### This project's test setup

- **Unit tests** (`tests/unit/**/*.test.ts`, helpers in `tests/helpers/`): vitest, `globals: true`, v8 coverage over `src/**`. Always use `tests/helpers/tmp.ts` for data dirs — never write to `~/.newsmonger`. API tests go through `createApp(...)` + `app.request(...)` (no real server). The AI provider is the deterministic `createMockProvider` (or an inline `fakeProvider`), wrapped as a `ProviderResolver` via `tests/helpers/provider.ts` (`asResolver`, `fakeProvider`).
- **The unit suite requires a build**, and `test-all.sh` runs both before vitest. `dist/client/` because several tests fetch `/static/…` through the real route (NEWS-191); `dist/cli.js` because `npm-package.test.ts` spawns the packaged CLI as `node dist/cli.js` (NEWS-295) — that is the artifact its assertions are about, it starts far faster than the `npx tsx` it replaced, and unlike tsx it needs no IPC socket, so **the unit suite runs inside a command sandbox**. It rebuilds the bundle itself when stale, so a bare `npm test` still works.
- **E2E tests** (`tests/e2e/**/*.spec.ts`): Playwright, **sharded by file since NEWS-321** — each worker boots its own `--ai-test` server, on its own port and pid+worker-scoped temp data dir, from a worker-scoped fixture (`tests/e2e/server.ts`). Playwright's `webServer` is *global* with no per-worker form, which is why the server is not in `playwright.config.ts` any more; `globalSetup` builds the client bundle once, before any worker exists. Whole files go to workers and every spec stays `mode: 'serial'`, so the unit of parallelism is the file. **`E2E_WORKERS=1` restores the serial run** and is the first thing to try when a failure smells like one shard interfering with another. Tests build on each other's state **within a file** (documented at the top of the spec); across files they must not — every file calls `resetSharedState` in its own `beforeAll` (NEWS-313), and a file that needs a topic with stories says so with `seedCheckedTopic` rather than inheriting one (NEWS-322).
- **`npm run test:all` still needs `dangerouslyDisableSandbox` on macOS, and the reason is now Chromium, not us** (NEWS-299). The E2E *server* is sandbox-safe as of NEWS-299 — `node --import tsx/esm`, the same loader without the `tsx` CLI's unix socket. What blocks the run is the browser: `bootstrap_check_in org.chromium.Chromium.MachPortRendezvousServer: Permission denied (1100)`. Chromium registers a Mach port at startup and the macOS sandbox refuses it, exactly as it does for `npm run demo:stills`. **Nothing in this repo can fix that**, so do not spend another ticket looking — see NEWS-311. Everything up to E2E (`gate:quick`, `npm test`, `npm run dev`) runs sandboxed. **A different engine is not the way out, and this has been measured** (NEWS-311): Playwright's Firefox does get further — `launch()` and `newContext()` both succeed where Chromium dies at launch — and then `newPage()` fails with an internal protocol error, because the content process it forks is what the sandbox stops. The same probe passes outside the sandbox, so it is the sandbox and not the install. Firefox trades one hard failure for a later, stranger one; the answer is still `dangerouslyDisableSandbox`.
- **Never use the `tsx` CLI** — `node --import tsx/esm` instead. Same loader, same source, same coverage; the CLI additionally opens a unix-domain socket to talk to its own child, and a command sandbox denies `bind()` on a unix socket *anywhere*, `$TMPDIR` included. Pinned by `tests/unit/sandboxable.test.ts`, because on a permissive machine every test passes either way — which is how the E2E line survived NEWS-295's fix of the unit one.
- **Spawn tools through `scripts/npm-command.mjs`** (NEWS-348, NEWS-354, NEWS-356). `tests/e2e/global-setup.ts` spawned a bare `npm`, which is `npm.cmd` on Windows — a shell shim, not an executable — so `execFile` threw `spawnSync npm ENOENT` before a single test ran and took the whole suite with it. Windows needs **both** the `.cmd` name *and* `shell: true` — Node has refused to spawn a `.cmd` without a shell since the CVE-2024-27980 hardening, so fixing only the name earns `EINVAL` instead of `ENOENT`, which cost a second failed beta. `npmSpawn()`/`npxSpawn()` return the pair together so a caller cannot take half. The rest of the harness is fine because it spawns `process.execPath`, a real binary everywhere; this is the only place a *tool* is named. **Windows E2E runs only in `release-candidate.yml`**, so a break here is invisible until a beta is cut — it cost a failed `v0.2.0-beta.16`, three days after the code landed. Pinned by `tests/unit/e2e-global-setup.test.ts` and a tree-wide scan in `tests/unit/windows-portability.test.ts`, both asserting about a platform they are not running on, for the same reason `sandboxable.test.ts` does — **and `sandboxable.test.ts` now walks the tree rather than a hand-kept list**, which is how `real-providers.spec.ts` kept its `npx tsx` (NEWS-356).
- **No source file may carry a raw control byte** (NEWS-403) — `tests/unit/control-bytes.test.ts`, the third member of that family and added for the same reason: the failure is invisible on the machine that introduces it. A literal `0x00` sat in `src/routes/api.ts` — every API route the app serves — which made `file` report it as `data` and made **grep and ripgrep skip the whole file silently** unless forced with `-a`. That cost a wrong conclusion during NEWS-397 ("there is no manual classification path"; there is, in that file), and it broke a UTF-8 boundary outside the repo when a ticket describing it was rejected by the Hot Sheet API. Walks `src/`, `tests/`, `scripts/`, `docs/` and the root-level prose — **`docs/` because this project greps its own docs as a workflow step**, and a requirements doc that vanished from search would break FR-id allocation while looking fine. Excludes binaries **by extension, never by "skip whatever fails to decode"**: a decode-failure skip would exempt the next mangled `.ts` for exactly the reason it exempts a PNG. **Scope is C0 plus DEL** — C1 controls, U+2028/U+2029, a mid-file BOM and the bidi-override class are all multi-byte in UTF-8, equally invisible, and *not* covered (NEWS-408).
- **Concurrent E2E is safe** (NEWS-287). The port is no longer the constant 4189 — `tests/helpers/e2e-port.ts` derives a **five**-port window per checkout by hashing the checkout path (one per worker plus the real-provider server, NEWS-321), so two worktrees, or an agent and a developer, can run the suite at once. Slots dropped 400 → 160 to pay for the wider stride, keeping the whole range inside 4200–4999; collision odds per pair of checkouts rose from ~1/400 to ~1/160, and the pre-flight still names one in a sentence. **Use `parallelIndex`, never `workerIndex`**, to pick a worker's port: `workerIndex` increments when Playwright replaces a crashed worker and would walk straight out of the window. `scripts/e2e-preflight.mjs` runs at config load and, when the port is held, either **reclaims** an orphaned server left by a crashed run or **stops with a sentence** naming what is there — instead of a raw `ECONNREFUSED` surfacing inside an unrelated spec several files later.
- **Commands**: unit `npm test` · E2E `npm run test:e2e` · everything `npm run test:all` (typecheck + lint + Rust + unit + E2E + coverage merge). Coverage report lands in `coverage/`, merged across all three legs by `scripts/merge-coverage.mjs` — see the coverage-merge bullet below.
- **The merged coverage report takes each file's executable-line set from the *unit* run** (NEWS-357) — it is the only source with real source-map remapping; c8's `LF` is the file's total line count, comments included, and unioning line numbers let that become the denominator. A source that reports **no unhit lines at all** is refused as unmeasured rather than merged — it is reporting "was loaded", not "was covered". The browser leg tripped that guard until NEWS-359: c8 cannot read a source-mapped `--format=iife` bundle and marked every client line covered, so `merge-coverage.mjs` converts that leg with `monocart-coverage-reports` instead, attaching the bundle source at merge time rather than in each of the 234 dumps. **This bullet lives here, in the `specifics` block, deliberately** — it was written into the managed *Coverage* bullet above and a sync ate it (NEWS-380).
- **`npm run test:e2e:scramble [seed]` runs the specs in a shuffled file order** (NEWS-314), to hunt the kind of cross-file dependency NEWS-313 found by accident — `keys.spec.ts` inheriting its precondition from `discover.spec.ts`'s last four lines. Playwright orders files alphabetically with no hook to change it, so the order is imposed by *name*: the specs are copied to a scratch dir with numeric prefixes and a wrapper config points `testDir` there. Everything else is the real config, because the leakage only exists when the files share a server. Not in any gate — run it after adding a spec file, or before touching the harness. Five seeds were clean when it was written.
- **`npm run test:all -- --from=<phase>` resumes** (NEWS-300). E2E is ~73% of a 3m34s run, so a failure there used to mean fixing one line and re-paying typecheck, lint, both builds and the whole unit suite to get back. `--list` prints the phase ids. **A resumed run is not a commit gate and says so** — every run ends with a summary naming each phase and whether it ran, a partial one prints a banner refusing to be mistaken for a full one, and a failure names the phase and hands you the `--from=` to resume with. Pinned by `tests/unit/test-all-phases.test.ts`, which cross-checks the summary against what actually executed: a wrong answer here would be a *green* run with a phase silently skipped, which this project has already had once.
- **`npm run gate:quick` is the iteration loop** (NEWS-294): typecheck + lint + client build + unit tests, no coverage, no Rust, no E2E. ~21 s against ~5 min, for the edit-run-edit cycle. **`npm run test:all` is still required before every commit** and the never-commit-red rule is unchanged — `gate:quick` is what you run *while* working, not what you run before committing. It prints that reminder itself, every time.
- **The Rust gates path-gate themselves** (NEWS-294). `scripts/rust-changed.sh` decides from the diff — uncommitted work plus commits not yet on the upstream — and `scripts/gates-rust.sh` skips `cargo fmt`/both clippy profiles/`cargo test` when nothing under `src-tauri/` (nor a Rust-adjacent script) differs. Every uncertainty resolves to *running* them; the skip is loud and says how to force it (`RUST_GATES=required`); and it is disabled outright when `CI` is set. This is a local-iteration optimisation and never a coverage reduction: `ci.yml`'s dedicated rust job calls cargo directly and always runs everything.
- **Recorded CLI sessions** (NEWS-277) — the default way to test a CLI provider. `tests/fixtures/cli-sessions/*.json` are real transcripts, captured once by `npm run record:cli-sessions` and committed; `tests/unit/cli-session-replay.test.ts` replays them through the **real** provider via `spawnRunner(name, exec)`. That runs the argv construction, the schema temp file, the parsing and the error formatting — all the code `config.runner` skips, and all the code that broke in NEWS-272/274. Fast, offline, in CI. Two of the five fixtures are deliberate *failures* (a removed flag; a schema strict mode rejects), because inventing an error payload is how a fixture gets the shape wrong in the way that hides the bug.
- **Real subscriptions**: `npm run test:e2e:real` (NEWS-276) runs `tests/e2e/real-providers.spec.ts` against the **actual** CLIs — its own server, no `--ai-test`. **Not in `test:all`**: a check may take the providers' 10-minute ceiling and spends plan quota. Skips per provider when the CLI isn't signed in, and always in CI.

  **The two layers do different jobs and both are needed.** A recording proves our *handling* stays correct; it cannot notice the vendor changing what it says — a frozen `--search` success would have replayed green for weeks. The live spec is the only thing that catches drift, so run it after touching a provider, and before cutting a release; then re-record, and read the fixture diff as the vendor's changelog.
- The real Claude request path and the Tauri shell are covered by `docs/manual-test-plan.md`.

## Requirements Documentation

Keep human-readable requirements documents as the source of truth for what the project does, and **keep them up to date in the same change as the code** (add/remove/modify a requirement → update its doc). Create new docs for major new functional areas. Cross-reference related docs with relative links.

### AI Summaries

Maintain two synthesis docs an AI assistant reads at the start of a fresh session — keep them in sync with reality (source doc/code wins on conflict), and prefer small targeted edits over rewrites:

- A **codebase map** — directory tree, entry points, data schema, build, tests, settings, and a "where do I look for X" index. Update it in the same change when you add a file or directory, add a route/endpoint, change the schema, add a client module, or add a setting key.
- A **requirements summary** — a synthesized view of every requirements doc with status markers (e.g. Shipped / Partial / Design only / Deferred). Update it in the same change when you add a requirements doc, ship a design-only feature, or defer/regress a shipped one.

### This project's docs layout

- Requirements docs: numbered `docs/N-topic.md` (currently 1–34; **19 is deliberately absent** — `19-cost-visibility.md` went with the spend removal in NEWS-119, and the number is not reused, same rule as an FR id), FR-N.M requirement ids, cross-referenced with relative links. - **An FR id is declared once, ever** (NEWS-302). - Manual test plan: `docs/manual-test-plan.md`.

  - `docs/ai/code-summary.md` — the codebase map. **Hand-written, and staying that way**: it is a judgement about what matters, and generating it would flatten it into a directory listing worth nothing. Update it in the same change as the code, per the general bullet above.
  - `docs/ai/requirements-summary.md` — **two halves**.   - Its **notes region is hand-written** and is the point of the file: what was decided and why, the traps, the caveats no marker can carry. The generator copies it through byte for byte. Add to it freely; just don't restate status there.

## Ticket-Driven Work

When the user gives you work directly (not via the Hot Sheet channel or events), create Hot Sheet tickets before starting implementation — especially for substantial or multi-step work.

- **Do create tickets** for: features, bug fixes, refactoring, multi-step tasks, anything changing code. **Don't** for: simple questions, git commits, quick lookups, trivial one-liners. **When in doubt, create them.**
- Create via the Hot Sheet API (prefer the `hotsheet_*` MCP tools), mark Up Next, then work through them: set status `started` → implement → set `completed` with notes.
- **Always create follow-up tickets** for incomplete work (unfinished steps, open design questions, known gaps, designed-but-unbuilt features). If it's not in a ticket, it's forgotten.
- **Incomplete-work checklist** — before marking a ticket `completed`, file follow-ups for any: (1) UI placeholder text ("coming soon"), (2) TODO/FIXME comments, (3) documented-but-unimplemented requirements, (4) empty/stub functions returning mock data.
- **Use FEEDBACK NEEDED before deferring or asking about follow-ups.** When about to (a) defer a ticket needing more work, (b) ask whether to file follow-ups, or (c) close with a question buried in notes — DON'T. Leave the ticket `started`, add a `FEEDBACK NEEDED:` note (per `.hotsheet/worklist.md`), signal channel done, and wait. It's the only reliable way to surface a question.
